## 1. 先讲清四件事

### 1.1 它不是改名的第 N 个模式，是一个**独立的「搬文件」子系统**

前六批都是「给一批文件算出新名字，原地改名」。本批**不改名**——它把一批文件**复制或移动到另一个文件夹**（按四种方式归类）。

所以它**完全不碰**现有的五模式 / 规则引擎 / 改名执行器（`rename-executor.ts`）。它有自己的：入口按钮（主工具栏）→ 独立对话框 → 自己的执行器（`merge-service.ts`）。

> ★ 形态上「独立对话框，不碰主流程」（拍板第 7 条）的准确含义：**不改动主界面和改名流程**，合并是一个单独打开的弹窗，关掉后对主流程零影响。

### 1.2 ★★ 递归摊平是「新能力」，不是沿用 —— 实测纠正

产品负责人以为「现在拖入文件夹就会递归挖到底摊平」。我实查了 `fs-scan.ts` 的 `resolvePaths`（第 68 行）：它是**一项对一项**——拖入一个文件夹，列表里就是**那个文件夹本身一项**，**不会**自动加进来里面的文件。

```
拖入 D:\素材\客户A  →  列表里只有「客户A」这一个文件夹项
                       （里面的照片、子文件夹都不会自动进来）
```

→ 所以「合并时递归摊平」是**本批要新写的 walker**（§7.1 的 `fs-walk.ts`）。这是本项目**第一次写递归**，必须和 `DEC-01` 的护栏对齐：**不跨 symlink / junction / 挂载点递归**（否则会死循环或把系统目录整块复制进来）。

### 1.3 与最高铁律「绝不覆盖」的关系 —— 本批**不开「覆盖」档**

安全底线第 ① 条从第 0 批起就是「**绝不覆盖**」（冲突默认跳过 + 标红 + 人来决定）。「合并」天然会遇到「目标已存在同名文件」—— 本批的处理是：**默认跳过 + 标红 + 在干跑报告里逐条列出**，与改名一致。

→ 本批**不提供「覆盖」选项**（那是给最高铁律开口子，必须单独评审，见 DEC-26）。合并类型里**没有**「覆盖」这一档。

### 1.4 撤销 —— 本批**不做**（拍板第 3 条）

现有 `F9` 撤销**只回滚改名**（`rename-executor.ts` 的 `undoEntries`，只处理 `RenameEntry`）。本批搬动文件后，`F9` 回滚不了。

→ 产品负责人拍板：**不做撤销，先干跑再说**。干跑报告是本批的替代安全网。给历史记录加「合并类型」（为以后做撤销预留正规路子）本批**不做**，留给 P3-8 之后统一评估（见 DEC-24 注）。

## 3. 完整定义

### 3.1 四种合并方式（各算各的落点）

目标根目录记为 `T`。每个源文件 `S` 的落点：

| 方式 | 落点规则 | 例子（`T = D:\整理后`，源 `D:\a\1.jpg` 创建于 2026-09-18） |
| --- | --- | --- |
| **① 只合并到同一目录** | `T\<原名>` | `D:\整理后\1.jpg`（扁平，不建子文件夹） |
| **② 按扩展名各建一个文件夹** | `T\<ext>\<原名>`（`ext` 不带点；无扩展名 → `无扩展名` 文件夹） | `D:\整理后\jpg\1.jpg` |
| **③ 按创建日期（到日）** | `T\<创建日YYYY-MM-DD>\<原名>` | `D:\整理后\2026-09-18\1.jpg` |
| **④ 按修改日期（到日）** | `T\<修改日YYYY-MM-DD>\<原名>` | `D:\整理后\2026-09-18\1.jpg` |

> ②③ 会在 `T` 下**新建子文件夹**；①④ 直接放进 `T`。四种方式**互斥**（单选）。

### 3.2 复制 vs 剪切

| 操作 | 源文件 | 实现 |
| --- | --- | --- |
| **复制**（默认，•） | **保留** | `fs.cp` 源 → 落点 |
| **剪切**（默认关） | **删除** | 先 `fs.cp` 到落点，**全部复制成功后再删源**（两阶段，见 §4 边界 4） |

### 3.3 目标文件夹

两种给法（拍板第 8 条，二选一）：
- **选已有**：从系统文件夹选择器挑一个已存在的目录当 `T`。
- **新建**：选一个父目录 + 填一个名称 → 在父目录下新建 `名称` 当 `T`（已存在则拒绝并要求改名）。

### 3.4 递归摊平（拍板第 6 条，新能力 DEC-25）

源里**拖入的文件夹**会被递归展开成里面的所有文件（不跨 symlink / junction）。护栏：
- **深度上限 20**（`FLATTEN_MAX_DEPTH`）
- **文件数量上限 10000**（`FLATTEN_MAX_FILES`）
- 超限 → 干跑报告报错（`EX-19`），**拒绝执行**

### 3.5 完成后打开目标目录（拍板第 9 条）

执行成功后用系统方式打开 `T`（Windows：`explorer` 打开该文件夹）。**默认勾上，可取消**。

## 4. 算法与边界

| # | 边界 | 预期行为 |
| --- | --- | --- |
| 1 | 目标已存在同名文件 | **跳过 + 标红**（绝不覆盖，§1.3）；干跑报告逐条列出 |
| 2 | 递归摊平跨 symlink / junction / 挂载点 | **不递归**（DEC-01 护栏，防死循环 / 防复制系统目录） |
| 3 | 摊平深度 > 20 或文件数 > 10000 | 干跑报 `EX-19` 并拒绝执行 |
| 4 | ★ 剪切（移动）中途失败 | **两阶段**：先确保**全部**复制成功，再删源。任一处删源失败 → 记 `EX-20` 半移动态、报告标红，**绝不**回滚已复制的文件（避免把已经安全的东西又删掉） |
| 5 | 日期分组用 UTC 还是本地 | **本地日期**（DEC-03：改名也用本地日期，本批一致）—— 跨午夜的文件进正确的「日」 |
| 6 | 无扩展名文件（方式 ②） | 归入 `T\无扩展名\` 文件夹（不建空名文件夹，否则建文件夹会失败） |
| 7 | 隐藏文件（如 `.gitignore`） | 正常归类（`.gitignore` → `无扩展名` 或按实际扩展名）；提示里说明「点文件也会算进去」 |
| 8 | 目标 `T` 落在某个源文件夹**内部** | **拒绝**（否则会尝试复制自己）→ 干跑报 `EX-20` 类错误 |
| 9 | 源与目标同盘 / 跨盘 | 都支持；同盘剪切退化为 `rename`（快），跨盘剪切 = 复制 + 删源 |
| 10 | 空源（没选任何文件） | 干跑报告直接提示「没有可合并的文件」，不打开执行 |
| 11 | 某个源文件读不出（权限 / 被占用） | 该文件在干跑报告里标记错误，其余照常；不中断整批 |
| 12 | 「完成后打开目录」时 `T` 不可 reveal（如网络盘断连） | 静默吞掉异常，**不影响主结果**（§7.3 第 8 行） |

## 5. 我主动加的判断（都说明理由）

**① ★ 干跑报告做成「硬要求」，不是可选项。**
总规划里我标过「强烈建议」，本批升为**必须**：因为搬动文件不可逆，先列清「会复制几个、跳过几个、错几个」再让用户点确认，是最后一道人眼闸门。这也让 §7.3 第 3 行的「预览 ≡ 执行」有落点。

**② ★ 不开「覆盖」档（DEC-26）。**
「合并」会遇到同名冲突，最省事是给个「覆盖」勾。但那直接违反第 0 批起的最高铁律「绝不覆盖」。本批只做「跳过 + 标红」，覆盖档留给**单独评审**（或永不做）。这是本项目第一次要给最高铁律开口子，必须显式记一条 DEC。

**③ ★ 递归 walker 第一次写，必须和 DEC-01 护栏对齐。**
`fs-scan.ts` 现有递归相关的护栏（不跨 symlink / junction）是为「防算文件夹大小死循环」写的。本批是**第一次主动递归**，更容易忘这条 → 在 `fs-walk.ts` 里显式 `if (isSymlink || isJunction) 不递归`。

**④ 合并做成「独立对话框、不碰主流程」（拍板第 7 条），我完全认同。**
好处：主改名流程零改动、零回归面；合并逻辑全关在 `merge-*` 里，以后 P3-8（文件提取）可以复用同一套 `fs-walk` / 干跑报告骨架。

**⑤ 纯函数 `merge-plan.ts` 放在 `shared/`（与改名引擎同级）。**
算落点的逻辑（四种方式 + 冲突检测）做成纯函数，主进程和（未来的）预览都调它 → **干跑报告和真执行不可能算出两个不同的结果**（§7.3 第 3 行）。同时它不 import `node:fs`，可被 `node --test` 直接单测（沿用 P3-1 起的「纯逻辑放 shared」约定）。

**⑥ 剪切的两阶段（先全复制，再删源）。**
移动若「边复制边删」，中途失败会留下「部分移动」：有的文件已在目标、源里也没了，找不回来。改成「先确认全部复制成功，再统一删源」，任何删源失败都标红报告，绝不回滚已复制项。

## 13. 决策留痕（产品负责人三轮原话）

> 九条结论见文首「★ 已拍板」表。下面保留原问题与他的原话，作为**决策留痕**。

**第一回合（类型 / 操作 / 撤销）**
- 一、「文件夹合并」那 4 种类型到底是哪 4 种？→ **1、只合并到同一目录；2、按文件类型合并；3、按创建时间合并；4、按修改时间合并**。操作方式有：复制或者剪切二选一。
- 二、是【复制】还是【剪切】？→ **两个都做，剪切默认关（推荐）**。
- 三、要不要做「移动 / 复制」的撤销？→ **不做撤销，先干跑再说（推荐）**。

**第二回合（类型分法 / 时间粒度 / 子文件夹）**
- ①「按文件类型合并」——「类」怎么分？→ **按扩展名各建一个文件夹，并且完成后自动打开存储目录位置**。
- ②「按创建/修改时间合并」—— 时间切到多细？→ **到日**。
- ③ 源文件夹里的【子文件夹】怎么处理？→ （原话以为「现在拖入文件夹就递归挖到底摊平」）→ **实际是本项目新能力，已纠正并配护栏**（§1.2 / DEC-25）。

**第三回合（形态 / 目标 / 打开）**
- 一、「文件夹合并」做成什么形态？→ **独立的一个对话框（推荐）**。
- 二、目标文件夹怎么给？→ **两个都支持（推荐）**（选已有 / 新建）。
- 三、「完成后自动打开存储目录」要不要给个开关？→ **默认勾上，可取消（推荐）**。
