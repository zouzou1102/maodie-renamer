## 1. 先讲清六件事

### 1.1 五模式 = 自定义 / 插入 / 替换 / 删除 / 导入

| 新模式 | 从哪来 | 一句话 |
| --- | --- | --- |
| **自定义** | = 现有 `rule`（「规则化」**改名**） | 前缀 / 后缀 / 序号 / 日期自己拼 |
| **插入** | **新增** | 在名字的第 N 个字符后**插入任意一段文字** |
| **替换** | = 现有 `replace` | 把 A 换成 B |
| **删除** | = 现有 `delete` | 删掉某段文字 |
| **导入** | = 第 4 批的表格能力**提升为模式** | 名字由表格给，规则引擎不参与 |

> **「…」是预留位**（以后可能加模式），**不是第六个**。产品负责人原话。
> **扩展名更改不是模式** —— 见 §1.6。

### 1.2 ★★★ 本批最大的风险：**兜底式代码会把新模式静默吞掉**

这是摸底读代码读出来的，也是本批**最值钱的一条**。现有代码里到处是这种写法：

```ts
// sanitize-rule.ts:78   ← 主进程的入口白名单
const mode = src.mode === 'replace' || src.mode === 'rule' ? src.mode : 'delete'
```

**加第 4、5 个值之后，`'insert'` 与 `'import'` 会走进那个 `: 'delete'` 兜底** ——

> 用户在界面上选了「**插入**」，主进程收到的却是「**删除**」→ **界面正常、行为完全错**。而且这次更隐蔽：**规则结构还在，只是模式错了**。

同一个形态在代码里**四处**（§7.5 前四行）：

| 位置 | 兜底成什么 | 后果 |
| --- | --- | --- |
| `sanitize-rule.ts:78` | `'delete'` | 插入 / 导入被当成删除 |
| `RulePanel.vue` 的 `v-if delete / v-else-if replace / **v-else**` | 「规则化」那套界面 | 选插入 却看到自定义的界面 |
| `stores/rule.ts:52` `r.mode === 'delete' ? r.delete.text : r.replace.find` | 取 `.replace.find` | 对**错误的字段**做正则校验 |
| `RulePanel.vue` 的 `!isRuleMode`（反向判断） | 当成「删除 / 替换那一类」 | 「区分大小写」「正则」开关会出现在插入 / 导入模式下 —— **显示了但引擎不看** |

> ★ **这是一类以前没归过的静默 bug：`「三选一」被写成「不是 A 就是 B」的兜底式代码`。**
> 它的危险在于：**加值的那个时刻看不出来** —— 编译过、类型检查过、测试全绿（因为老用例只覆盖老的三个值），**只有新值真的跑起来才发现**。
> → **修法**：把每一处都改成**正面判断**或**穷尽 switch**（`never` 兜底），让「漏了新值」变成**编译期错误**。这几处要逐个走一遍，**不许留 `else` 兜底**。

### 1.3 「自定义」= 现有 `rule`（「规则化」）**改名**

界面上现在是三个四字页签（`删除字符` / `替换字符` / `规则化`），本批变成**五个两字页签**（`删除` / `替换` / `自定义` / `插入` / `导入`）—— **两字标签在一排里更站得开**，比四字更好排。

> **一个副作用（要接受）**：历史记录里**已经写死了老叫法** —— `ruleSummary` 的返回值进了 `history.json`，那是**撤销的依据，不能改写历史**。
> → 所以界面上会**新老两种叫法并存**：新记录写「自定义」，老记录仍显示「规则化」。见 §2.5。

### 1.4 「插入」的确切定义

**在名字的第 N 个字符后插入一段任意文字。** 例：

| 原名 | 设置 | 结果 |
| --- | --- | --- |
| `报告.docx` | 在第 **2** 个字后插入 `2026` | `报告2026.docx` |
| `IMG_0001.JPG` | 在第 **0** 个字后插入 `新_` | `新_IMG_0001.JPG`（等价于前缀） |
| `报告.docx` | 在第 **99** 个字后插入 `_终` | `报告_终.docx`（**越界自动落到末尾**，不报错 —— 与 P3-1 的同一处理） |

**与「自定义」的边界（这就是产品负责人确认的那条）**：

| | 插什么 | 在哪 |
| --- | --- | --- |
| **插入模式** | **任意文字** | 第 N 个字符后 |
| **自定义模式**里的「插在第 n 个字符后」 | **只能是序号 / 日期变量** | 第 N 个字符后 |

→ 两者**不重叠**：一个是「插任意文字」，一个是「把序号/日期插到中间」。**互斥模式保证同一时刻只有一种路径。**

### 1.5 ★ 「导入」= 第五个模式，规则引擎**完全不参与** —— 这一条**收回**第 4 批评审里的一个决定

产品负责人原话确认：五模式**互斥**，**导入是其中一员**。

> ⚠️ **这要收回他在第 4 批评审里同意过的第 4 条**：那次同意的是「**表外的项保持按规则算**」（拖 100 个文件、表里 8 行 → 其余 92 个按规则改名）。
> 但「导入」既然是**五选一**的模式，选了它**规则引擎整个不参与** → 不存在「按规则算」这回事。

**现在定的语义（已拍板）**：

| 情形 | 行为 |
| --- | --- |
| 选了「导入」模式 + 表里有这一行 | 用**表里的新名** |
| 选了「导入」模式 + **表里没有这个文件** | **保持原名不动**（列表里标「表里没有，不参与」） |
| 选了**别的**模式 | **表格整个不生效**（连「本批有 8 个名字来自表格」那条提示条也不该出现） |

**所以本批有一件附带工作**：**回改第 4 批的设计文档与已上线行为**（把「叠加覆盖层」改成「互斥模式」）。§7.5 会单列这一条。

### 1.6 ★ 「扩展名更改」**不是模式** —— 它和「大小写转换」是同一类东西

**现状是一条结构性的铁律**（`shared/name-split.ts` 开头就写着「扩展名一律不参与任何规则 —— 这是默认行为，不是开关」）：

```
splitName(名字) → { stem, ext }
      ↓  规则只作用在 stem 上（引擎**从来看不到 ext**）
joinName(newStem, ext) → 完整名字
```

**扩展名保护之所以稳，不是因为有 `if`，而是因为规则引擎根本拿不到扩展名。**

而项目里已经有一个「作用在结果上的处理」的先例：**`caseTransform`（大小写转换）** —— 它**不是模式**，是 `RuleConfig` 里一个顶层开关（「先按模式算出主体，**最后**整体做大小写」）。

> **本批把「扩展名更改」按同一形状做**：`RuleConfig` 里一个顶层小组，**默认关**。
> - 关着 = 现在的行为，**一个字都不变**。
> - 打开 = 在 `joinName` 那一步，把传进去的 `ext` 换掉。
> **不是第 6 个模式** —— 理由：改扩展名通常要**配合**改名（先改主体、再改扩展名），做成模式就互斥了、没法一起用。

## 2. 界面形态

### 2.1 模式页签：3 → 5

```
┌─ 规则区 · 模式 ─────────────────────────────────────────┐
│  [ 删除 ] [ 替换 ] [ 自定义 ] [ 插入 ] [ 导入 ]         │   ← 5 个两字页签
└─────────────────────────────────────────────────────────┘
```

- 默认仍是 **`自定义`**（= 现在的 `rule`，默认模式不变）。
- 老用户打开软件：**页签数变了、两个名字变了，但他原来选的那一个还在原位**（`自定义` 就在 `规则化` 原来的位置）。

### 2.2 两个新模式的界面

**「插入」**（在既有规则区里，和删除/替换同一种形态）：

```
┌─ 插入模式 ─────────────────────────────────┐
│  在第 [ 2 ] 个字符后 插入 [ 2026       ]    │
│  示例：【素材】 → 【素2026材】              │
└────────────────────────────────────────────┘
```

**「导入」**：这个模式**本身没有输入框**，它是一个**入口 + 状态**：

```
┌─ 导入模式 ─────────────────────────────────────────────┐
│  名字由表格决定。                                      │
│  [ 选表格并导入… ]                                     │
│  ─────────────────────────────────────────────────     │
│  已导入「订单对照.xlsx」：8 个文件有名字                │
│  另外 92 个文件表里没有 —— 它们保持原名不动             │   ← ★ 一句话说清
│  [ 重新选表格 ]                                        │
└────────────────────────────────────────────────────────┘
```

**为什么必须写那句「另外 92 个保持原名不动」**：不写的话，用户会以为「我导入了，那 92 个也该改点什么」—— 又是一个「界面正常但行为不明」的迷局。

### 2.3 「扩展名」小组（默认关）

放在**「进阶设置」折叠区外面**（它虽然后默认关，但要能被看见 —— 藏进折叠区就等于没有），位置在「保留原文件名」附近：

```
┌─ 扩展名 ───────────────────────────────────────┐
│  [ ] 改扩展名                                  │   ← 默认不勾
│      [ 改成指定扩展名  ▾ ]  [ pdf ]            │   ← 勾上才出现
│      与「全部小写」互不影响：扩展名按你写的样子 │
└────────────────────────────────────────────────┘
```

- 那个下拉 **4 档**：`改成指定扩展名` / `删掉扩展名` / `在后面再加一个` / ——（`保持原样` = 不勾）。
- 输入框里**打不打点都行**（`pdf` 与 `.pdf` 等价，程序自动规范化）—— 少一处会打错的地方。

### 2.4 「只用编号」入口 —— **就是加一个内置模板**（零新机制）

P3-1 已经确认：**「只用编号作为文件名」现在就能等价做到**（取消「保留原文件名」+ 前后缀留空 + 不启用日期 + 启用序号）。所以本批**不需要新机制**，只需要一个**显眼入口**。

而 P2-B 已经有现成的入口：规则区**顶部那一行「常用规则」模板条**（点一下**整份替换** `RuleConfig`）。

> **本批只加第 7 个内置模板：「只用编号」** —— 点一下就把列表里的文件改成 `1`、`2`、`3`…（或按你之前设的编号类型）。
> **零新增 UI 机制、零新增通道、零新增持久化。** 这是这一小项的最优解。

### 2.5 历史页要加一句说明（因为 §1.3 的改名）

历史页里老记录的规则摘要会显示「规则化」，新记录显示「自定义」。要在历史页顶部加一句常显说明：

> 早期版本的记录里，「自定义」叫「规则化」—— 是同一个功能改了名字。

**为什么不直接把老记录也改成「自定义」**：那些摘要是**撤销的依据**（写进了 `history.json`），**改历史文本**等于动了撤销凭据 —— 本项目一贯不做。

## 3. 完整定义

### 3.1 五模式的定义与互斥

| 模式 | 值 | 新名主体怎么来 |
| --- | --- | --- |
| 删除 | `delete` | 从原名里删掉一段（支持正则） |
| 替换 | `replace` | 把原名里的一段换成另一段（支持正则） |
| 自定义 | `rule` | 前缀 + 日期 + [原名] + 后缀 + 序号（P3-1 的公式，**一个字不改**） |
| **插入** | `insert` | 在原名主体的第 N 个字符后插入一段文字 |
| **导入** | `import` | **来自表格**（引擎不参与；表里没有的项保持原名） |

**互斥仍然由 `RuleMode` 这一层保证**（`DEC-02` 的结论不变：用 `switch` 而非「顺序执行多条规则」）—— 只是**分支从 3 个变成 5 个**。

### 3.2 插入模式的算法与边界

```
结果 = [主体前 k 个码点] + 插入文字 + [主体后段]
k 按**码点**切（Array.from），不是按 UTF-16 单元
k < 0 → 当 0；k > 长度 → 落到末尾（不报错）
插入文字为空 → 规则不生效（等价于不改）
**扩展名永不参与**
```

> ★ 「按码点切」这一条是**照抄 P3-1 的教训**：P3-1 在实现 `seqPosition = 'at'` 时踩过 —— 直接 `slice(k)` 会把 emoji 劈成半个代理对，生成**非法文件名**。插入模式是同一件事，必须同样处理。

### 3.3 导入模式的语义

见 §1.5。补充三条边界：

| 情形 | 行为 |
| --- | --- |
| 选了导入模式，但**还没选过表格** | 列表里**每一项都「不改名」**，并在规则区提示「导入模式：还没选表格」。**不报错、不置灰主按钮**（用户可能是刚切过来） |
| 从别的模式**切到**导入模式 | **表格不自动生效** —— 要用户**主动点「选表格并导入…」**（不清空、不猜） |
| 从导入模式**切走** | 表格的对应关系**保留在内存里**（切回来还在），但**不生效**；顶部那条「来自表格」的提示条跟着消失 |

### 3.4 扩展名处理的完整定义

**四档**（互斥，由 `RuleConfig` 里一个新小组承载）：

| 档 | 例（原名 `报告.docx`） | 备注 |
| --- | --- | --- |
| **保持原样**（不勾 = 默认） | `报告.docx` | **现在的行为，一个字不变** |
| **改成指定扩展名** | 填 `pdf` 或 `.pdf` → `报告.pdf` | 最常见 |
| **删掉扩展名** | → `报告` | |
| **在后面再加一个** | 填 `bak` → `报告.docx.bak` | 例：做备份标记 |

**五条必须写死的边界**：

1. **文件夹不受影响** —— 文件夹没有扩展名概念（`splitName` 对 `isDir` 直接返回 `ext: ''`）→ 扩展名处理**对文件夹一律不生效**，保持原名。
2. **非法字符照样被挡** —— 新扩展名里如果有 `\ / : * ? " < > |`，会走既有的 `validateNewName` → 那一条**在列表里标红**（复用 `E_INVALID_CHAR`，**零新增错误码**）。
3. **和「大小写转换」互不干涉** —— 「全部小写」**只作用于主体**（既有铁律）；扩展名按**你写的样子**来。所以填 `PDF` 就得到 `.PDF`，想要小写就自己写小写。
   > 界面上要用那一行小字讲清（§2.3 版图里已写）。

   | 设置（同一个文件 `照片A.JPG`） | 结果 |
   | --- | --- |
   | 不勾「改扩展名」+ 全部小写 | `照片a.JPG` —— 扩展名一直不动（现在的铁律，本批不改） |
   | **改成 `.PDF` + 全部小写（甲 · 本设计的做法）** | `照片a.PDF` —— 主体变小写，扩展名**按你写的样子** |
   | 改成 `.PDF` + 全部小写（乙 · 另一种选择） | `照片a.pdf` —— 大小写**连扩展名一起管**（更省心，但要改一条既有铁律） |
4. **和导入模式的关系** —— 导入模式的新名**来自表格**，而表格那一套本来就只给**主体**（第 4 批定的）。所以**导入模式下扩展名处理仍然有效**（它是「结果处理」，和模式正交）。
5. **排序**：`按模式算出主体` → `拼回（可能被改过的）扩展名` → `校验` → `冲突检测`。**扩展名处理不影响主体**。

### 3.5 「只用编号」入口 = 一个内置模板

```
名字：只用编号
内容：mode='rule'，seqEnabled=true，keepOriginal=false，
      prefix=''，suffix=''，dateEnabled=false
效果：照片A.jpg → 1.jpg ；照片B.jpg → 2.jpg ；照片C.docx → 3.docx
```

**为什么用模板而不是新按钮**：P2-B 的模板机制**就是**「点一下整份替换 `RuleConfig`」—— 与「套用一组配置」是同一件事。**再加一个按钮就是造第二套机制。**（P2-B 当时也说过：套用后照样能接着手改。）

## 4. 算法与边界

| # | 边界 | 预期行为 |
| --- | --- | --- |
| 1 | 插入位置越界（填 99） | **落到末尾**，不报错（与 P3-1 的 `at` 同一处理） |
| 2 | 插入位置填 0 | 等价于**前缀**（插在最前面） |
| 3 | 插入位置填负数 | 当 0 |
| 4 | 插入文字为空 | 规则不生效（**不报错**，与 P0「空规则」一致） |
| 5 | 插入文字里带 `{n}` `{d}` `{创建}` 等 | **不替换** —— 插入模式**不认识变量**（变量是自定义模式的机制）。原样插入 |
| 6 | 插入在主体的第 N 个码点后，主体含 emoji | **按码点切**，绝不产生半个代理对（否则生成非法文件名） |
| 7 | 扩展名填成 `pdf.` / `.pdf.` / `..pdf` | **规范化成一个点**（`pdf.` → `.pdf`）；全是点时退化成空 → 等价「删掉扩展名」 |
| 8 | 扩展名填超长（>200 字符） | 走既有 `E_PATH_TOO_LONG`（复用，零新增） |
| 9 | 开了扩展名处理 + 文件**本来没扩展名** | `改成 .pdf` → `README.pdf` ✓；`删掉扩展名` → 不生效（本来就没有） |
| 10 | 开了扩展名处理 + **文件夹** | 一律不生效（§3.4 第 1 条） |
| 11 | 导入模式 + 表外项 | **保持原名不动**（§1.5） |
| 12 | 老配置（`mode:'rule'`）读进来 | **照旧工作** —— `'rule'` 这个值不变（只是界面上叫「自定义」）。**零迁移** |

## 5. 我主动加的判断（都说明理由）

**① `'rule'` 这个值不改名，只改界面上显示的字。**
改枚举值要动 `history.json` 里的旧摘要、CLI 的 `--rule` 语义、模板库、以及所有老单测 —— **全是纯风险、零收益**。界面上叫「自定义」，代码里仍是 `rule`，**在注释里写清这个映射**就够了。

**② 扩展名处理放在「保留原文件名」附近，不藏进进阶折叠区。**
默认关不等于可以藏。藏进去 = 这个功能等于没有（P2-C 那次「设置里有关闭动画的开关、但用户根本打不开设置」就是同一个教训）。

**③ 导入模式下，表外项在列表里逐条标出来，而不是只给一个数字。**
「保持原名不动」如果要靠用户自己数，就等于没说。给一个**小徽标**（复用 P2 那套），并在规则区写总数。

**④ 切模式时**不清空**任何东西。**
从自定义切到插入再切回来，前缀/后缀/序号那些设置**都还在**（`RuleConfig` 是一份完整配置，不是五个独立面板）。这与「空规则」的一贯处理一致，也是 P2-B 模板「整份替换」的反面：**手改的参数不该因为切页签丢掉**。

**⑤ 「只用编号」用模板实现，不加新按钮。**
理由见 §3.5：加按钮 = 造第二套机制。而模板本来就承诺「套用后还能手改」，正好满足「先用编号起个头、再改细节」。

## 7. 改动面

### 7.1 类型与字段

```ts
// src/shared/types.ts
export type RuleMode = 'delete' | 'replace' | 'rule' | 'insert' | 'import'

/** 扩展名处理（默认 'keep'，与 caseTransform 同级：作用在结果上的开关） */
export type ExtMode = 'keep' | 'set' | 'remove' | 'append'

export interface RuleConfig {
  mode: RuleMode
  // …既有字段一字不动…
  /** ★ P3-5 新增：扩展名处理 */
  extMode: ExtMode            // 默认 'keep'
  extValue: string            // 默认 ''；只有 set / append 用得到
}
```

**插入模式的参数 —— 单独一组**（产品负责人 2026-09-23 定的）：

```ts
  /** ★ P3-5：插入模式的两个参数 —— 单独一组 */
  insert: {
    at: number            // 默认 0：在第几个码点后插
    text: string          // 默认 ''：插什么
  }
```

> **为什么不塞进 `rule` 组**：`rule` 组现在是「**自定义模式**」的四个要素（前缀 / 后缀 / 序号 / 日期）。插入是**另一个模式**，把它的参数混进 `rule` 会让「哪个字段属于哪个模式」变模糊。**一组对应一个模式**更清楚 —— 这也正是产品负责人选「单独一组」的理由。
> 界面上自然也是**单独一个小组**（只在插入模式出现，见 §2.2 版图）。
> ⚠️ **不要**为此新造一套「模式专属字段」的抽象机制 —— 就是**多一个组**，与既有 `delete` / `replace` / `rule` 三个组并列。（`import` 没有参数，所以不需要组。）

### 7.3 扩展名处理的落点（★ 精确到行）

现在（`shared/preview.ts`）：

```ts
const newStem = computeNewStem(parts, rule, { index, total, date, seedKey: item.id })
const attemptedName = joinName(newStem, parts.ext)      // ← 这里传的是**原** ext
```

本批改为：

```ts
const newExt = extText(parts.ext, item.isDir, rule.extMode, rule.extValue)
const attemptedName = joinName(newStem, newExt)
```

**并且同文件里那两处必须一起改**（§7.5 第 6/7 行）：
- `stemOf(final, ext)` —— 它按**原 ext** 从末尾剥；
- `toResolveInput()` 用 `joinName(i.stem, i.ext)` 还原原名 —— 这是**还原**，仍用原 ext（**这里不要改**，它不是算新名）。
