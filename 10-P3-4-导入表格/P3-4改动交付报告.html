三、过程中发现并修掉的两个「坑」

这两个都不在设计清单里，是**做的时候撞上**的，都记进项目记忆了。

坑 1冒烟脚本里 feature() 的回调是【定义时】就执行的

我第一版新用例写的是「在执行到这一步时，临时把环境变量指向另一张表」：

feature('...', (c) => {
  process.env.SMOKE_IMPORT_PATH = 另一张表; // ← 以为是执行时才跑
  return c.click(...)
})

但 helpers.js:622 是 if (typeof build === 'function') build(makeRecorder(ops)) —— 回调只用来收集 ops，是在定义那一刻就跑完的。于是这句赋值在跑任何用例之前就把表换掉了 → 前面所有 P3-4 用例都拿到了错的那张表，一次挂 5 条。

教训：冒烟用例的回调里不能有副作用（改环境变量 / 改状态）。 要改就用 op 序列里的动作，或者提前在夹具区做好。

坑 2弹窗是 fade-in，而「等它出现」只等了尺寸

弹窗的可见性判定用的是 checkVisibility({ checkOpacity: true }) —— 含透明度。 而原来的等待条件只等「盒子有尺寸」，那个在第一帧就成立 → 断言撞在动画中间 （实测 可见=false 尺寸=115x39，尺寸正常但透明确实还没上来）。

修法：把等待条件改成「真的可见」（同一个 checkVisibility 判据）—— 这是把「动画还没跑完」从断言里排除，不是放宽断言。

顺带一条跑真机冒烟时别去操作别的窗口

中间有一轮，一条跟本批无关的老用例（P2-B 模板 chip 的悬停变色）红了： waitFor 超时(4000ms) —— backgroundColor === 'rgb(245, 166, 35)'。 原因是我在跑的同时操作了命令窗口，被测窗口被遮挡 → :hover 不生效。 全程不打扰它，那一轮就全绿了。这条也记进记忆了。
