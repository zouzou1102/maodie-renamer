二、这一批加了什么

能力说明
入口 左栏操作区多一个「导出清单」按钮，放在「清空列表」上面。 为什么不放底部的动作区：那里主按钮是「开始改名」，是全程序唯一会改文件的动作； 把不改文件的导出塞进去，会糊掉「主按钮 = 危险动作」这条视觉约定。
选项气泡 点开后三个选项：
· 格式：Excel(.xlsx) / 文本(.txt) / CSV(.csv) / Word(.docx)，默认 Excel
· 范围：全部 / 仅选中项（没勾任何文件时这一档是灰的）
· 列：原名 / 新名 / 状态（默认勾上）＋ 所在文件夹（默认不勾 —— 完整路径里可能有客户名、项目名，与「清空历史」出于隐私做入口是同一个理由）
四档格式 · xlsx：真表格，能排序筛选，拿去继续用
· txt：Tab 分隔，记事本直接看
· csv：通用纯文本表格
· docx：真表格 + 有边框 + 表头加粗 + 表头每页重复，能直接打印、能当正式附件交出去
零依赖 xlsx 与 docx 自己写（共用一个 ZIP 打包器），没有引入任何第三方库。 清单只有几 KB，为它引一个压缩库等于给「零运行时依赖」开个口子。

三、三条落盘安全底线（本批新立的硬规矩）

导出要往硬盘上写东西，所以定了三条 —— 这是「绝不覆盖」那条底线往导出场景的延伸：凡是要往硬盘上写东西，决定权必须在用户手里。

  • 一律走系统「另存为」对话框，由你亲手指定存哪 —— 程序绝不自己猜路径。
  • 绝不默认写到列表里那些文件所在的目录。你拖进来的多半是素材目录，凭空多一个清单文件就是污染。
  • 只新建，绝不静默覆盖。在对话框里选了已存在的文件时，由 Windows 自己问「是否替换」；程序不做任何额外的覆盖处理。

四、三处最容易「看着像好了」的地方（都已经堵上）

1预览还在算的时候就导出 → 拿到的是上一轮的新名

预览有 200 毫秒防抖 + 后台计算。如果你改完规则立刻点导出，导出的会是改动之前的名字 —— 而你看着屏幕上显示的新名，完全看不出哪里不对。这是本批最像 P2-A 那个坑的地方（值不对、界面却毫无异常）。

处理：「导出…」按钮在预览没算完时置灰，并在旁边写明原因（「正在重新计算，稍等一下」）， 不让你对着一个灰按钮猜。

2Word 那档：漏写一行声明，Word 会直接说「文件已损坏」

.docx 是一个压缩包，里面有一张「内容清单」必须把每个部件都登记上。 少登记一个（比如正文），Word 打开时会报「文件已损坏，无法打开」 —— 而我们自己的检查（只看压缩包结构与格式合法性）会全部通过。

处理：专门写了一条检查，把「内容清单里登记的东西」与「压缩包里真实存在的东西」 双向逐个比对 —— 少一个就红。

3txt / csv 的编码：不带 BOM 会让 Excel 里整张表中文乱码

没有开头那 3 个字节的标记，中文 Windows 上的 Excel 会按本地编码去猜，整张表的中文全是乱码。 更麻烦的是：这一条只在你那边看得出来 —— 我在这台机器上用 VS Code 打开是好好的。

处理：txt 与 csv 两条路径共用同一处加这个标记，并写了断言钉死开头 3 字节是 EF BB BF。

关于第 ④ 条：为什么必须真导一次

系统的「另存为」对话框是 Windows 原生窗口，自动化脚本点不到它 —— 不给个办法的话，「生成 → 写盘」这段真实代码在自动测试里永远走不到，等于本批核心功能没被验过。

所以测试脚本会在启动时注入一个落点，跳过对话框，让真实代码完整跑一遍。 生产环境没有这个变量，等价于这段分支不存在。这与项目里既有的「数据目录注入」是同一类做法。

九、本轮踩到并已记录的两个坑

已解决冒烟两次「跑一半就没了」

现象是进程在跑到一半时消失、没有任何报错。排查后确认：慢速冒烟全程约 2 分 14 秒，而命令执行有 120 秒上限， 超时就被截断（用一句「睡 150 秒」的命令单独验证过，同样在 2 分钟被切断）。 显式把上限调高之后，两轮都是 58/58 全过 —— 与代码无关。

本轮的代码编辑有几次报成功、实际没写进去（types.ts 的类型定义整块丢了）。 已改为「改完立刻用独立方式回读核对」，并发现过一处自己脚本写坏的行（把注释开头吃掉了）。 这类问题不会报错，只能靠改完再读一遍抓。
